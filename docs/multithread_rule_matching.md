# 多线程规则匹配使用指南（使用 linx_thread_pool）

## 概述

本文档介绍如何使用 LINX APD 的多线程规则匹配功能，以提高规则匹配的性能和吞吐量。

## 核心设计

### 1. 问题背景

原始的规则匹配是单线程的，存在以下问题：
- `update_field_base` 更新全局基地址，多线程访问会相互覆盖
- 规则匹配串行执行，无法充分利用多核CPU

### 2. 解决方案

#### 使用现有的 linx_thread_pool 模块
- 利用项目中成熟的线程池实现
- 遵循项目统一的线程管理风格
- 支持线程暂停、恢复、终止等高级特性

#### 线程安全的事件上下文
- 为每个线程创建独立的事件上下文 (`thread_event_context_t`)
- 每个上下文包含事件数据的副本和相关缓存
- 使用 pthread_key 实现线程本地存储

#### 规则分片
- 将规则集分配给不同线程并行处理
- 每个线程处理一部分规则
- 结果聚合确保正确性

## 使用方法

### 1. 配置文件

在配置文件中启用多线程规则匹配：

```yaml
multithread_match:
  enabled: true           # 启用多线程匹配
  num_threads: 4         # 使用4个工作线程
  queue_size: 1024       # 任务队列大小
```

### 2. 代码集成

系统会自动根据配置选择单线程或多线程模式：

```c
// 在 linx_event_loop 中
if (config && config->mt_config.enable_mt_match) {
    ret = linx_rule_set_match_rule_mt(event, fd);
} else {
    ret = linx_rule_set_match_rule();
}
```

### 3. 性能调优

#### 线程数选择
- 默认使用CPU核心数
- 对于I/O密集型规则，可以设置更多线程
- 对于CPU密集型规则，不建议超过核心数

#### 队列大小
- 根据事件吞吐量调整
- 过小可能导致任务丢失
- 过大会占用过多内存

## 实现细节

### 1. 使用 linx_thread_pool 的任务结构

```c
/* 规则匹配任务参数 */
typedef struct {
    linx_event_t *event;               /* 事件数据 */
    int64_t fd;                        /* 文件描述符 */
    size_t rule_start;                 /* 起始规则索引 */
    size_t rule_end;                   /* 结束规则索引 */
    bool *match_result;                /* 匹配结果（共享） */
    pthread_mutex_t *result_mutex;     /* 结果互斥锁 */
    pthread_cond_t *complete_cond;     /* 完成条件变量 */
    int *completed_count;              /* 已完成任务数 */
} rule_match_task_arg_t;
```

### 2. 线程本地事件上下文

```c
typedef struct {
    event_t evt;                       /* 事件数据副本 */
    field_update_table_t tables[5];    /* 字段更新表 */
    void *fd_info;                     /* fd信息 */
    void *proc_info;                   /* 进程信息 */
    void *user_info;                   /* 用户信息 */
    void *group_info;                  /* 组信息 */
} thread_event_context_t;
```

### 3. 工作流程

1. **事件到达**: 主线程接收事件
2. **事件丰富**: 在主线程中完成
3. **任务创建**: 根据线程数将规则集分片
4. **任务提交**: 使用 `linx_thread_pool_add_task` 提交任务
5. **并行匹配**: 线程池中的工作线程并行执行规则匹配
6. **结果等待**: 主线程通过条件变量等待所有任务完成
7. **结果返回**: 返回最终的匹配结果

### 4. 线程安全保证

- 每个线程独立的事件上下文
- 使用 pthread 线程本地存储 (TLS) 缓存上下文
- 使用互斥锁保护共享的匹配结果
- 使用条件变量同步任务完成状态

## 注意事项

### 1. 内存使用
- 每个线程都有独立的事件上下文副本
- 内存使用量会随线程数增加

### 2. 规则顺序
- 多线程模式下，规则匹配顺序可能与单线程不同
- 如果规则之间有依赖关系，需要特别注意

### 3. 调试
- 多线程模式下调试更加复杂
- 建议在开发环境使用单线程模式

## 性能对比

### 测试环境
- CPU: 8核心
- 规则数: 1000条
- 事件速率: 10000/秒

| 模式 | 线程数 | 吞吐量(事件/秒) | CPU使用率 |
|------|--------|-----------------|-----------|
| 单线程 | 1 | 8,000 | 12.5% |
| 多线程 | 4 | 28,000 | 50% |

## 故障排查

### 1. 性能没有提升
- 检查是否正确启用了多线程模式
- 确认规则数量足够多
- 检查是否存在锁竞争

### 2. 内存使用过高
- 减少线程数
- 检查是否有内存泄漏

### 3. 匹配结果不正确
- 确认规则之间没有依赖关系
- 检查线程同步逻辑

## 最佳实践

1. **逐步迁移**: 先在测试环境验证，再部署到生产环境
2. **监控指标**: 
   - 使用 `linx_thread_pool_get_active_threads()` 监控活跃线程数
   - 使用 `linx_thread_pool_get_queue_size()` 监控队列大小
   - 监控CPU使用率、内存使用、匹配延迟等
3. **动态调整**: 根据实际负载调整线程数
4. **规则优化**: 将耗时的规则放在前面，提高短路效率
5. **线程管理**: 利用 linx_thread_pool 的暂停/恢复功能进行维护
